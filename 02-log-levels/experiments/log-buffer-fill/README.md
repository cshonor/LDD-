# 实验：内核环形缓冲区填灌与覆盖观测（C 版）

> 真机：树莓派 5 / Debian 13 (trixie) / 内核 `6.18.34+rpt-rpi-2712`
> 结论文档：[`../../docs/kernel-log-buffer.md`](../../docs/kernel-log-buffer.md)
> 编译：`make`　运行：`sudo ./rbfill 700 50 200 RBPURE`

## 这个实验回答什么

1. 这台机器的 `log_buf` 到底多大？
2. 128 KiB 换算成"能装多少条 printk"是多少？
3. 覆盖什么时候发生、发生时能看到什么？

## 为什么必须用 C 写

不是形式问题，是这个实验**只有用 C 才能测准**。

关键在于：**`dmesg` 看到的 ≠ 缓冲区真实内容。**

| 读取方式 | 看到的是什么 |
|---|---|
| `/dev/kmsg`（本程序用） | 缓冲区里**最老一条存活记录**开始，全部内容 |
| `dmesg` / `klogctl(2)` | 走 `syslog(2)` 的游标 `syslog_seq`，只看**游标之后**的新消息 |

这直接导致两个坑：

**坑 1：`dmesg -C` 擦不掉任何东西。**

实测（清除前后立刻对比）：

```
              首条 seq   /dev/kmsg 条数   dmesg 条数
清除前          1235          619             1
sudo dmesg -C   ↓
清除后          1235          619             0     ← 只有 dmesg 变空了
```

`syslog_clear()` 只是把 `syslog_seq` 推到 `log_next_seq`，**记录一条没删、空间一点没腾**。
所以：

- `dmesg -C` 之后 `/dev/kmsg` 照样读出全部旧记录
- 也不能用 `dmesg -C` 来"腾地方"，新消息照样挤占旧记录的空间

**坑 2：`dmesg | wc -l` 不能用来判断缓冲区占用率。**

那是"游标之后还剩几条没读"，不是"缓冲区里有多少条"。
我第一版笔记就栽在这上面（据此错误推断"启动日志是被 clear 掉的"）。

## 覆盖检测：看 seq，不要看条数

常见的检测思路是"记录数回落 = 覆盖开始"，但这只在**缓冲区从不满到满**的那一瞬间有效。

问题是缓冲区**通常一开始就是满的** —— 因为用户态根本擦不掉它。
这种情况下记录数从头到尾纹丝不动，只能靠：

> **最老一条记录的 seq 有没有前进**

`seq` 是内核给每条记录的全局单调递增编号。seq 前进多少，就是被挤掉了多少条。
本程序在每次采样时记录 `oldest_seq`，一旦它变大就判定覆盖开始，并直接算出挤掉条数。

## 实测输出（节选，完整见 results.log）

```
已写入 记录总数 RBPURE数  最老RBPURE 首条记录(最老)
----------------------------------------------------------------------------
  基线     585      -        -        RBFLLB 00116 xxxx...
   50      585     50      00001     RBFLLB 00166 xxxx...   ★覆盖开始
  550      585    550      00001     RBFLLB 00666 xxxx...
  600      585    585      00016     RBPURE 00016 xxxx...   ← 上轮残留被清空
  700      585    585      00116     RBPURE 00116 xxxx...
```

`首条记录` 那一列的标签一路从 `RBFLLB` → `RBPURE` 变过去，
就是**覆盖边界一格格扫过缓冲区**的样子 —— 像履带在滚。

## 结论

| 项 | 实测值 |
|---|---|
| 缓冲区容量 | `klogctl(SYSLOG_ACTION_SIZE_BUFFER)` = **131072 B = 128 KiB** |
| 单条消息文本 | 214 B（`"RBPURE "` 7 + 5 位序号 + 1 空格 + 200 载荷 + 1 换行） |
| **稳态容纳条数** | **585 条** |
| 585 × 214 B | 125 190 B ≈ 122.3 KiB |
| 与 128 KiB 的差额 | 5 882 B（4.5%，每条记录的描述符 + 对齐开销） |
| 纯文本可用率 | **95.5%** |
| 本轮挤掉旧记录 | 700 条（seq 2969 → 3669） |

### 三个反直觉的点

**① 默认容量不是"几 MB"，是 128 KiB。**
差两个数量级。繁忙的内核（或一次带驱动探测的 `modprobe`）
几百条消息就能把你的调试输出冲掉。

**② 文本不是按 1 KiB 块对齐的。**
若按 1 KiB/条计，585 条需要 570 KiB，是容量的 4 倍多，早该溢出 ——
实测能装下。kernel 5.10+ 的 record-based ring buffer 是紧凑排布的，
每条只额外摊 ~10 B 开销（5882 / 585 ≈ 10.1 B）。

**③ 用户态无法真正擦除环形缓冲区。**
`dmesg -C` 只挪游标。想从空缓冲区开始观察增长，**只能重启**。

## 用法

```sh
make
sudo ./rbfill 700 50 200 RBPURE      # 700 条，每 50 条观察一次，载荷 200B，标签 RBPURE
```

| 参数 | 默认 | 说明 |
|---|---|---|
| 总条数 | 300 | 要灌多少条 |
| 每批观察数 | 16 | 每写多少条采样一次缓冲区 |
| 载荷字节 | 200 | 每条消息的有效载荷长度（≤3500） |
| 标签 | `RBFILL` | 换标签可区分多轮，避免编号混淆 |

想读"纯容量"，要保证灌完之后 `其它记录（非本轮）= 0`，
也就是灌的条数要**超过稳态容量**（585）。给 700 就够了。

## 收尾

```sh
sudo dmesg -C                          # 只挪游标，让 dmesg 不再显示测试消息
sudo timeout 5 cat /dev/kmsg | wc -l   # 缓冲区里其实还有 585 条
journalctl -k | grep -c RBPURE         # journald 里一条不少
```
