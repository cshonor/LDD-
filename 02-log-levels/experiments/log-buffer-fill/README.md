# 实验：内核环形缓冲区填灌与覆盖观测

> 真机：树莓派 5 / Debian 13 (trixie) / 内核 `6.18.34+rpt-rpi-2712`
> 结论文档：[`../../docs/kernel-log-buffer.md`](../../docs/kernel-log-buffer.md)

## 实验目的

回答三个没法靠读文档确定的问题：

1. 这台机器的 `log_buf` 到底多大？
2. 128 KiB 换算成"能装多少条 printk"是多少？
3. 覆盖到底什么时候发生、发生时能看到什么现象？

## 怎么做

`rbfill.sh` 往 `/dev/kmsg` 写定长消息（`<4>RBFILL 00042 xxxx…`），
每批调用一次 `dmesg` 观察：

- 缓冲区总行数
- 测试消息存活条数
- **最老那条是否还在**（被覆盖的判据）
- 缓冲区首行是什么

```sh
sudo ./rbfill.sh 300 16 200    # 写 300 条，每 16 条观察一次，每条 200B 载荷
```

两轮共写入 700 条（`300 + 400`），第二轮跑到缓冲区溢出。

## 看到了什么

`results.log` 是完整原始输出，关键片段：

```
已写入  缓冲区行数  RBFILL存活  首行
------------------------------------------------------------
  基线      57         -        [ 5739.296903] log_levels: module loaded
   250     607       550        [ 5739.296903] log_levels: module loaded   ← 还没满
   275     594       575        [58579.736998] input: INSTANT USB GAMING   ← ★覆盖开始
   300     584       584        [665415.594403] RBFILL 00017
   400     584       584        [665416.589487] RBFILL 00117
```

| 阶段 | 现象 | 判据 |
|---|---|---|
| 未溢出 | 行数线性增长（57 → 607） | 每条新消息都追加，无丢弃 |
| **溢出瞬间** | **行数回落**（607 → 594） | 7 天前的最老记录被静默丢弃 |
| 稳态 | 行数**锁死 584** | 每写 1 条挤掉 1 条，像履带 |

## 结论

| 项 | 实测值 |
|---|---|
| 缓冲区容量 | `CONFIG_LOG_BUF_SHIFT=17` → **131072 B = 128 KiB** |
| 单条消息文本 | 213 B（`"RBFILL 00117 "` 13 B + 200 B 载荷） |
| 最多容纳条数 | **584 条** |
| 584 × 213 B | 124 392 B ≈ 121.5 KiB |
| 与 128 KiB 的差额 | ≈ 4 KiB，描述符 + 对齐开销（约 3%） |
| 溢出后存活范围 | 共写 700 条，丢最老 116 条，存 584 条 |

### 两个反直觉的点

**① 默认容量不是"几 MB"，是 128 KiB。**
差了两个数量级。这意味着繁忙的内核（或一次 `modprobe` 带一堆驱动探测）
几百条消息就能把你的调试输出冲掉。

**② 文本不是按 1 KiB 块对齐的。**
若按 1 KiB/条计，584 条需要 570 KiB，是容量的 4 倍多，早该溢出 ——
但实测能装下。kernel 5.10+ 的 record-based ring buffer 是紧凑排布的。

## 附带发现：启动日志去哪了

实验前 `dmesg | head -1` 最早只到 `t=5739s`，而 `journalctl -k` 里
`t=2.519926s` 的启动消息还在。当时缓冲区只用了 **57 行 / 4 778 B**，
占用率 **≈3.6%**，远没满 → **不是被覆盖，是被 `dmesg -c` / `-C` 清空过**。

判别方法：缓冲区行数远低于 584 却丢了老消息，就是被 clear 了，不是被覆盖。

## 清理

```sh
sudo dmesg -C                 # 清掉测试消息
journalctl -k | grep RBFILL   # 验证 journald 仍留有全部 700 条
```
